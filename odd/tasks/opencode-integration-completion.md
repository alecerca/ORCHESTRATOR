# OpenCode integration completion — providers, models, credentials

## Objective
Let a user see and control, from Orquestador, the OpenCode surface that today is only reachable by pressing Ctrl+P inside the OpenCode TUI: providers, model selection, credential / API-key management, and afterwards the rest of the config surface.

## Problem
The app surfaces only two OpenCode domains: **skills** and **sessions**. There is no notion of provider, model, credential, agent definition, MCP server, or config editing anywhere in the Rust backend or the React frontend (verified: zero matches for `provider|credential|api key|mcp` across `src-tauri/`, `crates/`, `frontend/src/`).

`ModelRef { providerID, modelID }` exists (`crates/orquestador-core/src/types.rs:122`, `frontend/src/types.ts:37`) and `PromptBody.model` exists (`types.rs:813`) but is **never populated** (`PromptBody::text` sets `model: None`, `types.rs:850`), and `send_message` takes no model parameter (`src-tauri/src/commands.rs:289`). So every message runs on the server default model with no way to change it.

## Why
User request (2026-10-16): *"vamos a completar todo lo relacionado con opencode … tenemos que tener por ejemplo los provider, que los usuarios puedan cambiar de modelo y agregar las api key de los modelos que quieran en vez de atarlos a uno solo, en fin basicamente todo lo que se hace al presionar ctrl+p dentro de opencode"*.

## Evidence (verified, not to be re-derived)
- The installed `opencode serve` (`http://127.0.0.1:4096`) serves an **OpenAPI 3.1.0** document at `/doc` with **162 paths**. Credential/provider/model surface available:
  - `GET /provider` — provider list; `GET /provider/auth` — auth methods / status per provider
  - `PUT /auth/{providerID}` · `DELETE /auth/{providerID}` — **set / remove provider credentials (API keys)**
  - `POST /provider/{providerID}/oauth/authorize` · `POST /provider/{providerID}/oauth/callback` — OAuth connect
  - `GET /config/providers` · `GET,PATCH /config` · `GET,PATCH /global/config`
  - `GET /api/provider` · `GET /api/provider/{providerID}` · `GET /api/model`
  - `POST /api/session/{sessionID}/model` — per-session model switch
  - `POST /tui/open-models` — what Ctrl+P does for models in the TUI
  - Also present: `/mcp` (+ `/mcp/{name}/auth*`), `/agent`, `/command`, `/skill`, `/tui`, `/lsp`, `/formatter`
- Our HTTP layer: one typed client `OpenCodeClient` (`crates/orquestador-core/src/client.rs:96`); base URL from `server.json` / env (`client.rs:75-81`); Basic auth only when a password is set (`client.rs:175`); project scope via header `x-opencode-directory` (`client.rs:35,178`); SSE on `/event` consumed by `EventHub` (`crates/orquestador-core/src/events.rs`) and bridged to the webview as `CORE_EVENT` (`src-tauri/src/lib.rs:21,50`).
- Command pattern to copy: `list_skills` — Rust `#[tauri::command]` (`commands.rs:683`) → `generate_handler![…]` (`src-tauri/src/lib.rs:122`) → `invoke` wrapper (`frontend/src/commands.ts:108`).
- The app **never** reads or writes `opencode.json` / `auth.json`; its only OpenCode filesystem access is read-only skill roots (`src-tauri/src/commands.rs:520-524`). Doctrine: *"The app never mutates another tool's config"* — `docs/ARCHITECTURE.md:104`.
- Declared-but-deferred: `docs/ROADMAP.md:272` lists "Per-user model / API-key handling when one server serves many users" under **Out of scope / open questions**.

## Scope
**In scope**
1. Read providers, their models, and per-provider auth status.
2. Select the model used by a session (and a default), instead of being tied to one.
3. Add / remove provider API keys, and connect providers via OAuth.
4. Then: the remaining Ctrl+P surface — config read/patch, MCP servers, agents, slash commands.

**Out of scope (for now)**
- Multi-user credential separation (still deferred in `docs/ROADMAP.md:272`).
- Themes, keybinds, LSP/formatter settings (revisit after Phase 1).
- Any change to the video/README/release surface.

## Constraints
- **Doctrine resolved deliberately**: credentials are written **through the server API** (`PUT /auth/{providerID}`), so the *server* owns the write; the app must still never edit `~/.config/opencode/auth.json` itself. `docs/ARCHITECTURE.md:104` gets a clarifying note, not a silent contradiction.
- **Secret hygiene**: `/provider` and `/config` responses may embed configured key material in provider `options`. DTOs must deserialize only the fields we need and must never carry, log, or render an API key value.
- No new dependency unless justified in the commit message.
- The frontend has **no test runner** (no vitest/jest/jsdom). Its gate is `npx tsc --noEmit` + `npm run build`.
- **Backend gate**: `cargo check --manifest-path src-tauri/Cargo.toml` (compiles `orquestador-core` **and** the app crate) + `cargo test -p orquestador-core`. A root `cargo check` / `cargo test` **never compiles `src-tauri`** — it is deliberately not a workspace member — so a root-only check can pass while the app crate is broken.
- Conventional Commits with scopes, no AI attribution, no emoji.

## ⚠️ T11 operational requirement (verified live, 2026-10-17)
The clarification batch **never fires** unless the OpenCode server exposes the `question` tool. Verified against `opencode serve` 1.18.35:
- The tool is registered when `["app","cli","desktop"].includes(client) || OPENCODE_ENABLE_QUESTION_TOOL` — with the default `client="cli"` the registration half is already satisfied, so the env var is **not** required.
- What actually gates it is the **permission**. With no `question` key the tool is absent from the agent's toolset and the model gets `Model tried to call unavailable tool 'question'`.
- Fix (one line in `opencode.json`): `{ "permission": { "question": "allow" } }`. Confirmed live: with only that line (env var unset) the agent produced a real 3-question batch in one call, `GET /question` returned it, a **partial** reply (`[["Option A"],[],["free text"]]`) returned `true`, the list cleared, and the agent resumed with a summary — execution continued, never terminated.
- Live shape confirmed to match our DTOs exactly: `{id, sessionID, questions[{question,header,options[{label,description}]}], tool{messageID,callID}}`.
